# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Casework Drawing Analyzer: a FastAPI + React tool for testing how well LLMs detect cabinets, elevations, countertops, and elevation callouts in architectural casework PDFs. It's the "run the benchmark" companion to the ground-truth data in `../dataset` and the annotation tool in `../annotation_tool` (see the parent repo's `CLAUDE.md`) — upload a drawing, iterate on a prompt against a chosen model, and export results in the same `obj-count.json` / `obj-location.json` shapes used elsewhere in that repo.

Every model is routed through [OpenRouter](https://openrouter.ai)'s single OpenAI-compatible endpoint, so adding a model is a `config.yaml` entry (or just typing a slug into the UI's model picker) — not a code change.

## Commands

Docker (primary workflow):

```bash
cp .env.example .env   # set OPENROUTER_API_KEY
docker compose up --build
```

- Frontend: http://localhost:5173, Backend: http://localhost:8000 (docs at `/docs`).
- **Both Dockerfiles bake source in at build time — `backend/app` and `frontend/src` are NOT live-mounted.** Only `config/`, `prompts/`, and `data/` are volume-mounted. Any backend or frontend code edit requires `docker compose up --build -d [backend|frontend]` to take effect in the running stack; editing files on the host alone does nothing until rebuilt.
- `config/` and `prompts/` changes alone only need `docker compose restart backend` (no rebuild).

Local dev without Docker:

```bash
# backend (Python 3.11+)
cd backend && python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

# frontend (Node 20+)
cd frontend && npm install
VITE_API_BASE_URL=http://localhost:8000/api npm run dev   # or: npm run build / npm run preview
```

There is no test suite and no lint script configured for either side — don't go looking for one.

## Architecture

**Request flow:** Upload (`POST /api/upload`) validates the PDF (magic bytes + size limit) and renders it page-by-page to PNG via PyMuPDF (`fitz`) at the chosen DPI (`zoom = dpi / 72.0`), saved under `data/sessions/<session_id>/`. Analyze (`POST /api/analyze`) sends each selected page's PNG + the current system/user prompt to the selected model via `OpenRouterProvider`, bounded by an `asyncio.Semaphore` (`analysis.concurrency_limit`), with retry/backoff on transient errors. The response is parsed (`services/parser.py`), stored in the in-memory `SessionStore`, and can later be aggregated into export formats (`GET /api/sessions/{id}/export/{count,locations}`).

**Settings merge two sources at startup** (`core/config.py`): env vars (`.env` — secrets/paths only) and `config/config.yaml` (models list, defaults, DPI, concurrency — meant to be edited freely without touching code). Per-request UI values (model, temperature, prompt, DPI) override the yaml defaults; they never change what's on disk except via two explicit save paths, both writing to `data_dir` (not `prompts/` or `config.yaml`, which are read-only in Docker): the "Save as default" prompt endpoint (`data_dir/custom_{system,user}_prompt.txt`), and models added from the UI's model picker (`data_dir/custom_models.json`, via `Settings.add_custom_model`/`remove_custom_model`). Unlike the yaml-sourced `self.models` (cached once at startup), `Settings.custom_models()` re-reads that JSON file on every call, since it can change at any time without a restart — `Settings.all_models()`/`find_model()`/`model_ids()` always combine both sources, so callers should use those rather than `self.models` directly.

**Provider abstraction is one seam** (`services/llm_client.py`): `LLMProvider.analyze_image(...)` is the only method; `OpenRouterProvider` is the only implementation and already covers most vendors since OpenRouter proxies them behind one API. Adding a *model* is a `config.yaml` entry (or a `POST /api/models {"id": "vendor/slug"}` call, which the UI's "Add model" field wraps) with a valid OpenRouter slug — no code change, and no validation against OpenRouter's catalog before adding; a bad slug just fails naturally at analyze time. Adding a *provider* that bypasses OpenRouter means implementing `LLMProvider` and registering a factory in `_PROVIDER_FACTORIES`; nothing else (routes, frontend) needs to change, since `analyze.py` resolves the provider by name (`ModelOption.provider`) at request time. A model whose `provider` has no registered factory fails cleanly with "Unknown LLM provider" at analyze time rather than pretending to work — that's the intended way to list a model as not-yet-wired-up (see the `implemented` flag on `ModelOption`, which the frontend uses to label such options; distinct from the `custom` flag, which just marks a model as removable from the UI).

**Coordinate system — read `prompts/detector_system.txt` before touching anything bounding-box-related.** The model's raw response is a single JSON **object** with exactly one key, `"bounding_box"`, holding an **array** of detections: `{"bounding_box": [{"y_min", "x_min", "y_max", "x_max", "label", "confidence"}]}`. Coordinates are flattened directly onto each detection (no nested box sub-object) and normalized **0-1000 integers** relative to the image's own width/height (not 0-1 fractions, not raw pixels; `(x_min, y_min)` is top-left, `(x_max, y_max)` bottom-right). This is rescaled to real pixels — `(value / 1000) * dimension` — independently in three places that must stay in sync: the frontend preview canvas (`BBoxCanvas.jsx`, using the canvas's own rendered pixel size), the results table (`ResultsSummary.jsx`, using the focused page's known width/height), and the benchmark export (`parser.build_location_export`, using each page's stored dimensions). `confidence` (0-1 float) is captured and displayed (`ResultsSummary.jsx`'s table, `BBoxCanvas.jsx`'s label) but not used for filtering or scoring anywhere. The model does **not** count objects (the prompt doesn't ask it to) — per-category counts are computed downstream by tallying `label` values in `parser.parse_model_response`, using `LABEL_TO_CATEGORY` to map the model's singular labels (`cabinet`, `countertop`, `elevation`, `elevation_callout`) to the plural category names (`cabinets`, `countertops`, ...) used by `config.yaml`'s `categories`, `ExportCountResponse`, and the frontend summary tiles.

This has changed shape twice already (bare array of `{"bounding_box": {x_min,...}}` → this one), each time because a real model's/user's actual output didn't match what was asked for. `parser.parse_model_response` is deliberately lenient about the *previous* shapes too (a bare array at the top level, or a nested `bounding_box`/`bbox`/`bounding_2d`/`box_2d` sub-object on a detection get flattened up — see `_flatten_nested_box`) since both are unambiguous to interpret and models have drifted back to a prior schema's shape before. Don't assume the current flat shape is final; check what's actually being returned before extending this.

**This app's internal schema is not the benchmark's on-disk schema.** `ParsedResult`/`DetectedObject` (`models/schemas.py`) hold the model's native 0-1000-normalized representation; only at the export boundary (`build_count_export`, `build_location_export`) does it get converted into the flatter, pixel-space `obj-count.json` / `obj-location.json` shapes that match `dataset/project-*/prj*-obj-{count,location}.json` in the parent repo. Don't conflate the two when adding conversion or scoring code.

**Prompt files are not all mutually consistent — check which pair is actually wired in `config.yaml`'s `defaults.system_prompt_file`/`user_prompt_file`, *and* check `data_dir/custom_{system,user}_prompt.txt` first, before assuming a prompt file is live.** A saved custom prompt (via the UI's "Save as default", `PUT /api/prompt`) always wins over the yaml-referenced file (see `Settings.default_system_prompt_text`/`default_user_prompt_text`) -- it's easy to edit `prompts/detector_system.txt` and see no effect in the running app because of this, as happened once already. `prompts/detector_system.txt` (current yaml default) defines the schema above and is generic across object types; it pairs with a per-task user prompt that names the label(s) to find — currently `prompts/cabinet_user.txt` (cabinet-only; a user's own saved custom pair has since diverged from this to target countertops instead, which is expected/fine, not a bug). Older, now-unused pairs kept around for reference: `prompts/system.txt`/`andrian_prompt.txt` (0-1000 `"box"` array wrapped in `{"objects": [...]}`) and `prompts/default.txt`/`default_user.txt` (0-1-normalized `bbox:{x,y,width,height}`, model-supplied counts). Don't resurrect any of these without also reverting the schema/parser changes they assumed.

**`parser.parse_model_response` is deliberately lenient, not strict** — real models reliably produce almost-but-not-quite the requested schema: a misnamed key (`y.min`, `y` alone), a nested box sub-object instead of flattened fields, or occasionally outright broken JSON syntax partway through an otherwise-fine array. It falls back to the `json_repair` library when plain `json.loads` fails, flattens a nested box sub-object onto the detection if one shows up (`_flatten_nested_box`), rewrites known key aliases (`_KEY_ALIASES`) before validation -- canonical keys always win over aliases when a malformed object has both (seen: duplicate/conflicting `"y"` and `"y_min"` in the same object) -- and validates each array entry independently so one bad detection doesn't fail the whole page. What it does *not* do is guess at semantically-wrong values -- `DetectedObject`'s coordinate fields enforce the documented 0-1000 range (`Field(ge=0.0, le=1000.0)`), so a detection with a value outside that range is dropped rather than silently rescaled on a guessed assumption about what scale was intended. `parse_error=True` only when zero detections survive validation, not on the first bad one.

**A truncated response (hit `max_tokens`) still shows whatever was parsed.** `PageResultViewer.jsx` used to hide the annotated canvas entirely whenever `result.truncated` was true, even though the resilient parser above often recovers a complete, valid prefix of detections from a response that just got cut off mid-array (the incomplete trailing object is dropped like any other invalid entry). Now it shows the truncation warning *and* the annotated image/Raw JSON view together whenever `result.parsed.objects` is non-empty, falling back to raw-text-only when nothing survived. Same treatment for a genuine `parse_error` with partial recovery. Watch for the eager-evaluation trap this had once already: don't hoist a JSX block that reads `result.parsed.objects` above the `!result.parsed` guard — it must only be referenced (e.g. behind a function call) once `hasObjects`/a clean result already guarantees `parsed` is non-null.

**"The source image cannot be decoded" has two completely unrelated causes with identical wording — check which one you're actually looking at.** `services/image_utils.py`'s `downscale_image` (constants `MAX_DIMENSION`/`MAX_PIXELS`) exists because a large-format sheet at high DPI (e.g. a 42x30in sheet at 300 DPI is 12600x9000px, 113MP) is too big for two independent consumers:
  1. Some vision models reject an image that large outright (seen with Qwen2.5-VL via OpenRouter) — `analyze.py` downscales the copy sent to the model for this. A model's `bounding_box` values are normalized to *whatever image it received*, so shrinking the outgoing copy doesn't affect the rescaling math described above.
  2. The **browser's own `HTMLImageElement.decode()`** (in `BBoxCanvas.jsx`) can reject an image that large with the exact same error message. This was initially misdiagnosed as an OpenRouter/model-side problem (the wording is indistinguishable, and it seemed to correlate with whichever model was selected purely by coincidence) before realizing the failure was actually happening client-side, after a perfectly good API response, while trying to decode the full-resolution original for the preview canvas. Fixed by `pdf_processor.py` precomputing a downscaled `display_image_path` for every page at upload time (via the same `downscale_image`), which `GET /sessions/{id}/pages/{id}/image` serves instead of the full-resolution `image_path`. `PageRecord.width`/`height` are untouched by this and stay the true full-resolution values, since export-boundary pixel math (`parser.build_location_export`, `ResultsSummary.jsx`) depends on them.

  If this exact error resurfaces: check whether the analyze call actually returned a result first (cause 2, frontend/canvas) or never got a model response at all (cause 1, backend/API) before assuming it's the same one as last time.

`OpenRouterProvider._is_retryable` in `llm_client.py` also treats an `openai.APIStatusError` containing this message as retryable (alongside `RateLimitError`/`APIConnectionError`/`InternalServerError`, which are retried by exception type instead of message text) -- harmless to keep, but note it was written while cause 1 (the model/API side) was still suspected as the culprit for failures that were actually cause 2.

**Reasoning/"thinking" models draw internal reasoning tokens from the same `max_tokens` budget as visible output, before writing a single character of it** -- confirmed directly: Gemini 2.5 Pro spent 195 of a 200-token budget on reasoning for a one-word "hello" (finish_reason `length`, no answer at all), and 4788 of 4972 tokens on the real detection prompt. This is very likely *the* most common cause of "I raised max_tokens and it still truncated." `OpenRouterProvider._create_completion` in `llm_client.py` disables reasoning by default (`extra_body={"reasoning": {"enabled": False}}`) since bounding-box extraction doesn't benefit from it -- confirmed to fully eliminate reasoning tokens and fix truncation for models where it's optional (Kimi K3: 65→0 reasoning tokens). Some models reject this outright with "Reasoning is mandatory for this endpoint and cannot be disabled" (seen: GPT-5, Gemini 2.5 Pro, Gemini 3.1 Pro Preview, Gemini 3.5 Flash) -- caught by matching that message text (not a hardcoded model list, since which models require it isn't something this app controls or can keep in sync) and retried once with `{"exclude": True}` instead, which every model tolerates but only hides the reasoning trace from the response body, it doesn't stop the token spend. For those models, truncation from reasoning is not fixable from this app's side beyond raising `max_tokens` a lot or picking a different model. `AnalysisResult`/`PageResult` carry `reasoning_tokens`/`completion_tokens` through to the frontend specifically so `PageResultViewer.jsx` can tell a user *why* a truncated response happened (heavy reasoning spend vs. genuinely too many detections for the budget) instead of just saying "raise max_tokens" every time.

**Session state is in-memory, not persisted** (`services/session_store.py`) — a single-user local benchmarking tool, so a process-lifetime dict is deliberately simpler than a database. Rendered PNGs on disk under `data/sessions/<id>/` outlive the process, but session/result metadata does not survive a backend restart.

**History is one JSON file per analyze run**, not a shared append-only log (`services/history_store.py`), because concurrent analyze requests (bounded by the semaphore above) would need locking around a single file. Written once per `POST /analyze` call (not per page, since every page in a request shares model/temperature/prompt/dpi) under `data_dir/history/`; read-only via `GET /api/history`.

**Frontend state lives entirely in `App.jsx`** and is threaded down via props — there's no state management library. Toolbar settings (model/temperature/DPI/max tokens) each live behind their own popover button in `Toolbar.jsx`, closed via a shared `mousedown` document listener checking each popover's ref.

**"Cutting" mode (overlapping-tile detection) splits one page into a grid of overlapping crops sent as ONE combined request, instead of one whole-page image.** Toggled via `Toolbar.jsx`'s "Cutting" popover (next to DPI): Rows/Cols (default 3x3, 1-6) plus an Overlap % (default 25, under an "Advanced" disclosure). When on, `AnalyzeRequest` carries `cutting/grid_rows/grid_cols/overlap_pct`; when off, none of these fields are sent (matching the existing `category` optional-field convention in `api.js`) and the original single-image path in `analyze.py`'s `analyze_one` is completely untouched. All tiling-specific logic lives in `services/tiling.py`, self-contained and removable:
  - `compute_tile_grid` divides the full-resolution page (`page.image_path`, NOT `page.display_image_path` — crop boxes must be recorded against the same resolution `page.width`/`page.height` describe) into a rows x cols grid, expanding each cell by `overlap_pct` of its own size on every side so an object straddling a grid line ends up fully contained in at least one tile.
  - `crop_and_resize_tile` downscales (never upscales) a tile to `TILE_MAX_EDGE` (1568px, Anthropic's own vision-endpoint auto-resize threshold) if its long edge exceeds it — applied as a universal constant regardless of which OpenRouter-routed model is selected, since it's a downscale-only cap that's harmless even for vendors with looser limits.
  - `augment_prompt_for_tiling` appends a fixed instruction (requiring a `tile_id` field per detection, e.g. `"r0c1"`) to the request's `user_prompt` at request time only — never written back to `prompts/*.txt` or a saved `data_dir/custom_user_prompt.txt`, exactly like Multi-Prompting mode's per-category prompts.
  - `llm_client.OpenRouterProvider.analyze_tiles` sends all tiles as separate image content blocks (each preceded by a `"Tile r0c1 (row 0, col 1)"` caption) in one request, ending in one copy of the augmented prompt — unlike `analyze_image`, there's no single "main image", the tiles collectively replace it. Both methods share a `_send_messages` tail so the reasoning-disable/exclude fallback dance and retry logic (see below) are implemented exactly once.
  - `remap_tile_detections` converts each detection's tile-local 0-1000 coordinates back to full-image 0-1000 coordinates using that tile's recorded crop offset and pre-resize size — the resize scale factor cancels out algebraically in this formula (kept on `TileMeta` for diagnostics only, not because the math needs it). A detection whose `tile_id` doesn't match any known tile is dropped, not guessed at.
  - `merge_overlapping_detections` collapses same-label detections (from different tiles) whose full-image boxes have IoU >= `DEFAULT_IOU_THRESHOLD` (0.5) into their union (not intersection — either tile may have clipped the object at its own crop edge) with the higher confidence, so an object seen from two overlapping tiles doesn't get double-counted.
  - The result is an ordinary `ParsedResult`/`PageResult`, identical in shape to the non-cutting path — `BBoxCanvas.jsx`, `ResultsSummary.jsx`, and `parser.build_location_export` need zero tiling awareness. `DetectedObject.tile_id` (optional, added for this feature) is `None` on the non-cutting path and cleared to `None` once a detection is merged across tiles.

  `max_tokens` is deliberately NOT auto-scaled by tile count (a real risk, since the same budget now covers every tile's detections in one response) — instead, `App.jsx` computes a `maxTokensWarning` (comparing `maxTokens / (gridRows*gridCols)` against a rough `TOKENS_PER_TILE_ESTIMATE` floor, duplicated as a comment in `tiling.py` for the same reasoning) and shows it inline in the Cutting popover as a nudge, never blocking the send.

  Cutting composes with Multi-Prompting (`AnalyzeRequest.category`) with zero special-casing, since `analyze_one` branches on `cutting` first and only then applies `relabel_for_category` to whichever `ParsedResult` either branch produced — but each of Multi-Prompting's parallel per-category requests tiles independently, so a 3x3 grid with 4 active categories means 4 separate 9-tile requests, not one combined request across categories.

**"AI-crop" mode is a two-pass alternative to Cutting, mutually exclusive with it** (`AnalyzeRequest.ai_crop` vs `cutting` — `AnalyzeRequest`'s `model_validator` rejects a request setting both; the frontend also keeps them mutually exclusive via `App.jsx`'s `handleCuttingChange`/`handleAiCropChange`, each clearing the other). Where Cutting splits a page into a uniform overlapping grid, AI-crop asks the model to first find the page's own tagged regions, then only detects objects within those:
  - **Pass 1** sends the whole page (same whole-page downscale as the non-cutting path) with `AnalyzeRequest.crop_prompt` — the UI's editable "Crop prompt" field (`PromptEditor.jsx`, rendered only when AI-crop is on, same `CollapsibleField` component/styling as System/User prompt), asking the model to bound every tagged grid cell and extract its detail-tag text (`DetectedObject.text`, e.g. `"66 VENDING - NORTH ELEVATION"`). This is independent of `user_prompt` (the request's real object-detection task) — that's Pass 2's job. `crop_prompt` defaults to `ConfigResponse.default_crop_prompt` on page load (`Settings.ai_crop_cell_prompt_text()`, reading `config.yaml`'s `defaults.ai_crop_cell_prompt_file` — `prompts/elevations_unfiltered.txt` by default) so out-of-the-box behavior is unchanged; a request that omits or blanks `crop_prompt` falls back to that same default server-side (`analyze.py`: `request.crop_prompt or settings.ai_crop_cell_prompt_text()`), so a direct API call still works without it. Unlike `system_prompt`/`user_prompt`, there's no "Save as default" persistence for this field (no `data_dir/custom_crop_prompt.txt`) — it's request-scoped state only, following the same App.jsx-state → `analyzePages()` payload pattern, just without the custom-override file layer.
  - **Filter**: `services/ai_crop.py` drops any Pass-1 cell whose `text` contains "floor plan" (case-insensitive) — filtering happens in our own code now, not the prompt. `prompts/elevations_unfiltered.txt` is a copy of the original cell-detection prompt, `prompts/elevations.txt`, with that filtering instruction deliberately removed; the original file is untouched and still used wherever it was before.
  - If zero cells survive (no cells found, or all filtered out as floor plans): the response is `status: done` with an empty `parsed` and a human-readable `PageResult.ai_crop_message` (a real, successful outcome — not `parse_error`/`ERROR`) — Pass 2 never runs.
  - **Crop**: each surviving cell's box is converted to full-image pixels and padded by a small fixed percentage (`ai_crop.CROP_PADDING_PCT`, clip-avoidance only, not overlap-for-continuity like Cutting's grid, since these are already-distinct, non-overlapping sheet regions Pass 1 located), then cropped/resized via `crop_utils.crop_and_resize` — the same crop/resize helper Cutting uses (see below), given a sequential `cell_id` (`cell0`, `cell1`, ...) assigned by our own code, not the model's own possibly-colliding circled numbers.
  - **Pass 2** batches every surviving crop into ONE request via `llm_client.OpenRouterProvider.analyze_tiles` — reused as-is from Cutting mode, since "N images each with a caption, ending in one prompt" is exactly the same request shape. Each image is preceded by a caption of the exact form `"IMAGE {n} — cell_id: {cell_id}"` (1-based `n`; `tag_text` is deliberately NOT part of the caption, it's backend/frontend display metadata only). This pass uses the request's REAL `system_prompt`/`user_prompt` (the user's actual configured object-detection task), with `ai_crop.PASS2_INSTRUCTION` appended — which explicitly tells the model to ignore the system prompt's `"bounding_box"` envelope description for this response and instead return a top-level JSON **array** with exactly one entry per image, in order: `[{"cell_id": "...", "detections": [{"label", "bbox": {"x_min","y_min","x_max","y_max"}, "confidence"}]}]`, coordinates 0-1000 normalized relative to that image only.
  - **No full-page coordinate remap.** An earlier version of this feature converted each crop's detections back into full-page pixel coordinates using the stored crop box; that remap was found to be unreliable in practice and has been removed entirely. Detections now stay in each crop's own 0-1000-normalized space, and the frontend draws them directly on that crop instead of overlaying them on the full page (`CropsCarousel.jsx`, not `BBoxCanvas.jsx`, renders AI-crop results). Because there's no shared full-page space to merge into, `PageResult.parsed.objects` is always empty for an AI-crop result (so `parser.build_location_export`/`obj-location.json` has no entries for those pages — a known, deliberate consequence, not a bug); `parsed.counts` is still tallied from every crop's detections, so the Results summary tiles and `obj-count.json` still show real numbers.
  - **Verification, not silent alignment.** `services/ai_crop.py`'s `parse_pass2_response` parses Pass 2's raw text into that top-level array (its own parser, since this shape doesn't match `parser.parse_model_response`'s "bounding_box" envelope or bare-array shapes; per-detection validation still goes through the shared `parser.validate_detection`, extracted out of `parse_model_response`'s own loop for exactly this reuse). `_build_verified_crops` then checks: (1) does the returned array's length match the number of crops sent — if not, every crop is marked `verified: false` and a top-level message explains the mismatch, but detections are still kept where Pass 2 did return something (best-effort, matched by position); (2) does each entry's echoed `cell_id` match the `cell_id` expected at that position — a specific entry failing this check is marked `verified: false` too, again without discarding its detections. A crop is `verified: true` only when both checks pass. This message flows through the same `PageResult.ai_crop_message` field Pass-1's zero-cells case uses (both are successful, informative outcomes, never `parse_error`/`ERROR`).
  - **`services/crop_utils.py`** holds `crop_and_resize` (`CROP_MAX_EDGE` = 1568px, same Anthropic-endpoint reasoning as before), shared by both Cutting and AI-crop's cropping step — extracted out of `tiling.py` (which now just thinly wraps it) so the two features can't silently drift apart on this shared math. `crop_utils.remap_normalized_box` still exists and is still used by `tiling.py`/Cutting (which keeps its full-page overlapping-grid design, unaffected by AI-crop's redesign) — `ai_crop.py` no longer imports it.
  - `PageResult.crops` (a list of `CropInfo`: `cell_id`, `tag_text`, base64-encoded PNG, crop-local `detections`, `verified`) carries every crop actually sent to Pass 2, powering the frontend's crops carousel (`CropsCarousel.jsx`) entirely from already-held response state — no extra network round trip to view them, no server-side file storage. `PageResultViewer.jsx`'s view-toggle drops "Annotated image" entirely in favor of "Crops" whenever `result.crops` is non-empty, since there's nothing meaningful to draw on the full page for this mode.
  - Multi-Prompting composes with AI-crop the same way it does with Cutting (each category's request runs its own independent two-pass pipeline; `mergeCategoryResults.js` and `parser.merge_page_results` both concatenate `crops` arrays across categories, no dedup).

**Multi-Prompting mode fires one independent request per category instead of one request for the whole page.** Toggled via `PromptEditor.jsx`'s "Multi-Prompting" button, which swaps the single user-prompt textarea for 4 (one per `MULTI_PROMPT_CATEGORIES` entry in `multiPromptCategories.js`: cabinets, elevations, countertops, elevation_callouts). `App.jsx`'s `handleAnalyzeMulti` first calls `POST /sessions/{id}/reset-results` (clearing any prior stored results for the selected pages, so re-running doesn't pile detections on top of a previous run) then fires one `analyzePages(...)` per non-empty category prompt in parallel via `Promise.allSettled` (not `Promise.all`, deliberately — one category's failure must not block the other three), each tagged with `category: <key>` in `AnalyzeRequest`.
  - **Backend**: `analyze.py` sees `request.category` set, relabels every detection in that response to the category's canonical singular label (`relabel_for_category` in `parser.py`, via `CATEGORY_TO_LABEL`) overriding whatever label the model actually used, and stores it via `session_store.set_result(..., merge=True)` instead of overwriting — `SessionStore.set_result`'s merge path calls `parser.merge_page_results` to combine the incoming category's detections/counts/token-usage/raw-response with whatever's already been merged in for other categories of the same page (all under the same lock, so concurrent per-category writes for one page can't race). A category that fails or fails to parse doesn't fail the merged result — it's recorded in `PageResult.category_errors` (`{category: message}`) while `status` stays `DONE` as long as at least one category succeeded.
  - **Frontend**: `mergeCategoryResults.js`'s `mergeCategoryResponses` does the same combine independently, client-side, from the settled promises — this duplicates the backend's merge logic on purpose: the backend merge is what makes `SessionStore`/exports correct, but the frontend needs its own copy to render immediately without an extra round-trip to re-fetch what the backend just merged. Both must agree on what "merged" means if either changes.
  - `PageResultViewer.jsx` renders `result.category_errors` as small inline warnings ("`<category>` request failed — retry? (`<message>`)") alongside whatever categories did succeed, rather than failing the whole page's render.
  - The 4 category prompt values live in `App.jsx`'s `categoryPrompts` state (not derived from `userPrompt`), specifically so toggling Multi-Prompting off and back on doesn't lose what was typed. Each of the 4 fired requests still creates its own history entry (`history_store.py` records per-`POST /analyze` call, and each category is a separate call) — not deduplicated/merged in history, only in the session's stored results and exports.
